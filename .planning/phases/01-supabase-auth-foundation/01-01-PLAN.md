<objective>
Deliver the application-side half of the secured per-user data path: the three `@supabase/ssr` client factories (browser, server, middleware) plus a root `middleware.ts` that refreshes the session cookie on every request.

Purpose: DATA-02 ("a user can read and write only their own row") and DATA-03 ("photos never publicly accessible") are only enforceable from application code once a cookie-aware, JWT-attaching server client exists — RLS scopes every query to `auth.uid()`, which requires a verified session that only these clients + middleware provide. This plan builds that enforcement layer (ROADMAP Phase 1 success criterion #3). The SQL half ships in plan 01-02; the end-to-end proof is in plan 01-03.

Output: `lib/supabase/{client,server,middleware}.ts`, root `middleware.ts`, and the `@supabase/ssr` install (with `@supabase/supabase-js` bumped to satisfy its peer dependency).
</objective>

## Phase Goal

This is a pure-infrastructure phase (no UI, no end-user surface). The MVP "vertical slice" here is the **complete secured per-user data path**, not a user-facing feature. Framed as an infrastructure outcome:

> **As** the Campus Crush application, **I need** each student's profile data and face photo stored in an RLS-protected, per-user-scoped store reachable only through a cookie-aware, JWT-verifying Supabase client, **so that** Phase 2 sign-in and Phase 3 onboarding can persist private data safely with no later migration.

Because this environment has no live-DB access, the closest analog to a failing end-to-end test is the two-account + public-URL verification in plan 01-03. This plan (01-01) builds the client/middleware spine of that path.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Next.js server | Session cookie arrives from an untrusted client on every request |
| Next.js server → Supabase Auth | JWT must be verified server-side before any identity is trusted |
| developer machine → npm registry | Third-party package code is executed at install/build time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-01-SC | Tampering | `npm install` of `@supabase/ssr` + `@supabase/supabase-js` | mitigate | Blocking-human legitimacy checkpoint (Task 1) verifies `supabase`-org publisher + first-party repo on npmjs.com before install; packages have no postinstall script; lockfile diff is reviewable |

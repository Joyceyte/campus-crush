<objective>
Complete the sign-in round trip and make the app state-aware: the OAuth callback exchanges the code, verifies the email server-side against the partner-university list, rejects non-partner accounts, and routes everyone else to the screen that matches their account state. Add the protected shell, the placeholder destinations, and sign-out.

**User story:** **As a** Melbourne uni student, **I want to** come back from Google already signed in and land on the right screen, **so that** I can pick up exactly where my account is — and be told clearly if my email is not eligible.

Purpose: this is the enforcement plan. AUTH-02 is meaningless until a server-side gate exists; FORM-01 is meaningless until something reads the `profiles` row. Both must be trusted server-side data, never client self-report.

Output: `/auth/callback`, `/auth/signout`, `lib/auth/guard.ts`, the `(authed)` route group with `/onboarding` and `/confirmation` placeholders, and a sign-out control on every authenticated page.

**Locked decisions honoured in this plan** (from `02-CONTEXT.md`):
- The domain allowlist is enforced server-side in `app/auth/callback/route.ts`, NOT via a Postgres "Before User Created" hook. This is a locked STATE.md decision; do not add an auth hook. Plan 02-03 adds a database-layer backstop that is compatible with this decision.
- Profile-row existence is the routing/completion signal — there is no `profile_status` column and none is to be added.
- The domain check uses the JWT-verified email, never a client-supplied value.
- Sign-out is a route handler at `/auth/signout`, callable from any authenticated page via a small `SignOutButton` component.
- Protected-routing enforcement lives in a server component/layout, per CLAUDE.md's "gate in a server component/layout" guidance; middleware only refreshes the session (Phase 1).
- `/onboarding` and `/confirmation` get minimal placeholder pages so routing is provable end-to-end; Phases 3 and 4 fill them in.

**Prerequisite this plan does NOT assume away:** `supabase/profiles.sql` from plan 01-02 has NOT been confirmed applied to the live Supabase project (plan 01-03 is `status: deferred`). Until it is applied, the `profiles` select in `lib/auth/guard.ts` will error. The guard therefore treats a query error as "no profile row" and logs it, so an unapplied schema degrades to "route everyone to onboarding" instead of crashing the app. The apply itself is a checkpoint in plan 02-03.

Exports:

- `ALLOWED_REDIRECT_HOSTS` — a `readonly string[]` containing `campus-crush.org` and `www.campus-crush.org`.
- `resolveAppOrigin(request: Request): string` — reads the `x-forwarded-host` header. If present AND (it is in `ALLOWED_REDIRECT_HOSTS` or it ends with `.vercel.app`), return `https://<that host>`. In every other case — header absent, header unrecognised, header forged — return `new URL(request.url).origin`. Add a comment explaining why the allowlist is required: `x-forwarded-host` is caller-controllable outside the Vercel proxy, so trusting it unconditionally would turn every redirect in this file into an open redirect. Exception: when `new URL(request.url).hostname` is `localhost` or `127.0.0.1`, always return the request origin so local dev on port 3002 works regardless of headers.
- `destinationForProfile(profileExists: boolean)` — returns the literal `"/confirmation"` when true, `"/onboarding"` when false. Type the return as `"/onboarding" | "/confirmation"`.
- `getStudentSession()` — an async function wrapped in React's `cache()` (`import { cache } from "react"`) so repeated calls within one request hit Supabase once. It: awaits `createClient()` from `@/lib/supabase/server`; calls the JWT-validating current-user lookup (`supabase.auth.getUser()`, the only call permitted for an authorization decision per CLAUDE.md — the cookie-reading alternative is explicitly forbidden because it does not round-trip to the Auth server); returns `null` if there is no user or the user has no `email`; returns `{ user: null, eligible: false }`-shaped data is NOT used — instead, if `isPartnerUniEmail(user.email)` is false, return `{ user, profileExists: false, eligible: false }`; otherwise query `supabase.from("profiles").select("id").eq("id", user.id).maybeSingle()`, and return `{ user, profileExists: Boolean(data), eligible: true }`. If the query returns an error, `console.error` it with a message naming `supabase/profiles.sql` as the likely unapplied migration, and treat `profileExists` as `false` rather than throwing — an unapplied schema must degrade to "send them to onboarding", not a 500.
- `requireStudent()` — async. Calls `getStudentSession()`. If it returns `null`, call `redirect("/login")` from `next/navigation`. If it returns a session with `eligible: false`, call `await supabase.auth.signOut()` (obtain the client via `createClient()`) and then `redirect("/login?error=domain")`. Otherwise return `{ user, profileExists }`. Add a comment stating this is the second enforcement layer required by CLAUDE.md for any account that was created before the callback gate existed, or whose eligibility changed.

**B. `app/auth/callback/route.ts`** — `export const dynamic = "force-dynamic"` and a single `export async function GET(request: NextRequest)`.

Flow, in this exact order:
1. `const origin = resolveAppOrigin(request)` and `const url = new URL(request.url)`.
2. Define a local `back = (query: string) => NextResponse.redirect(new URL(`/login?error=${query}`, origin))`. Every failure path returns `back("oauth")` — never an error string derived from the provider, so nothing attacker-controlled reaches the browser.
3. If `url.searchParams.get("error")` is non-null (the student cancelled or Google refused), return `back("oauth")`.
4. Read `const code = url.searchParams.get("code")`. If it is null or empty, return `back("oauth")`.
5. `const supabase = await createClient()` from `@/lib/supabase/server`.
6. `const { error: exchangeError } = await supabase.auth.exchangeCodeForSession(code)`. If `exchangeError`, `console.error` it and return `back("oauth")`.
7. `const { data: { user } } = await supabase.auth.getUser()` — re-read the identity through the JWT-validating lookup rather than trusting the object the exchange returned. If there is no `user` or no `user.email`, `await supabase.auth.signOut()` then return `back("oauth")`.
8. `if (!isPartnerUniEmail(user.email))` — `await supabase.auth.signOut()` to destroy the freshly minted session, `console.warn` a message that records the matched-nothing outcome WITHOUT logging the full address (log only the portion after the `@`), and return `NextResponse.redirect(new URL("/login?error=domain", origin))`.
9. Query `supabase.from("profiles").select("id").eq("id", user.id).maybeSingle()`. On error, `console.error` and treat as no row.
10. Return `NextResponse.redirect(new URL(destinationForProfile(Boolean(data)), origin))`.

Read NO other query parameter. Specifically: the handler must not read `next`, `redirect_to`, `returnTo`, `state`, or any similar caller-supplied destination — the destination is derived solely from `destinationForProfile`. Add a comment recording that this is deliberate open-redirect prevention by construction, and that plan 02-01's sign-in button correspondingly sends no such parameter.

**C. `app/auth/signout/route.ts`** — `export const dynamic = "force-dynamic"` and only `export async function POST(request: NextRequest)`. Do not export a `GET`; Next.js then answers a GET with 405, which is the desired behaviour (a link or prefetch must never be able to end a session). Body: `const supabase = await createClient(); await supabase.auth.signOut(); return NextResponse.redirect(new URL("/login", resolveAppOrigin(request)), { status: 303 });`. The 303 is required so the browser follows the redirect with a GET rather than re-POSTing.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/auth/callback` | Every query parameter and every request header on the OAuth return leg is attacker-controlled |
| browser → `/onboarding`, `/confirmation` | Unauthenticated and non-eligible callers can request these paths directly |
| browser → `/auth/signout` | Any origin can attempt a cross-site form POST |
| Next.js server → Supabase Auth | JWT validation happens here; a cookie read alone is not a validation |
| Next.js server → Postgres `profiles` | The read is RLS-scoped to `(select auth.uid()) = id` |
| Vercel proxy → Next.js server | `x-forwarded-host` is trustworthy only when it comes from the platform proxy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Elevation of privilege | `app/auth/callback/route.ts` | mitigate | The email used for the eligibility decision comes from `supabase.auth.getUser()`, which round-trips to the Auth server to validate the JWT — never from a query parameter, form field, or the object returned by the exchange. A non-partner address triggers `signOut()` before the redirect, so the freshly minted session is destroyed rather than left live. Asserted by the `signOut` count and `isPartnerUniEmail` greps. |
| T-02-07 | Elevation of privilege | `app/(authed)/*` | mitigate | `requireStudent()` re-runs the identity and domain checks on every protected render. This is CLAUDE.md's mandated second layer: it catches any `auth.users` row created before the callback gate existed, and any session whose eligibility changed. Middleware is deliberately NOT the enforcement point — it only refreshes the session (Phase 1) and has no trusted `profiles` access. |
| T-02-08 | Tampering | callback redirect target | mitigate | The handler reads no caller-supplied destination at all. The destination is a literal produced by `destinationForProfile()`. Asserted by a grep returning 0 for `next`/`redirect_to`/`returnTo`/`redirectTo`, and by the Playwright test that supplies `next=https://evil.example.com` and requires the final URL origin to remain `http://localhost:3002`. |
| T-02-09 | Spoofing | `resolveAppOrigin()` | mitigate | `x-forwarded-host` is honoured only when it matches `ALLOWED_REDIRECT_HOSTS` or the `.vercel.app` preview pattern; anything else falls back to the request's own origin. Without this, a forged host header would rewrite every `NextResponse.redirect` into an off-site redirect carrying the user away mid-auth. Asserted by the forged-host Playwright test on the `location` header. |
| T-02-10 | Repudiation / Elevation | every auth decision in this plan | mitigate | Only the JWT-validating current-user lookup is permitted for authorization. The unverified-cookie alternative is banned outright by CLAUDE.md and asserted absent by a comment-stripped grep across `app/auth/callback/route.ts`, `app/auth/signout/route.ts`, and `lib/auth/guard.ts`. |
| T-02-11 | Spoofing | `/auth/signout` cross-site POST | accept | A forced sign-out is the worst outcome: no data is written, read, or destroyed, and the student simply signs back in. Two properties already blunt it — the route is POST-only (a link, image, or prefetch cannot fire it) and `@supabase/ssr` writes its session cookies with `SameSite=Lax`, so a cross-site POST does not carry them and the call is a no-op. Adding a CSRF token to a no-op logout is not warranted at ASVS L1 for this risk. |
| T-02-12 | Information disclosure | `console.warn` on domain rejection | mitigate | Only the portion of the address after the `@` is logged, so a rejected student's full email never lands in Vercel's log retention. The redirect itself carries no identifier. |
| T-02-13 | Information disclosure | `profiles` row read in `lib/auth/guard.ts` | accept | The select is `.eq("id", user.id)` under an RLS policy that already restricts rows to `(select auth.uid()) = id`, so the query cannot disclose another student's existence. The only fact revealed to the caller is whether their own profile exists — which is exactly what the routing decision must expose. |
| T-02-14 | Denial of service | unapplied `supabase/profiles.sql` | mitigate | The `profiles` select is failure-tolerant: an error is logged with the migration filename and treated as "no row", so an unapplied Phase 1 migration degrades to "everyone goes to onboarding" instead of throwing a 500 on every authenticated page. No `[ASSUMED]`/`[SUS]` package is introduced. |
